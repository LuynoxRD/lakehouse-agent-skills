# Monthly event parts

Three months of orders written as one Parquet file per month, the ordinary shape a dataset takes
before anybody decides it is a table. Every value is **synthetic**: the orders come from a fixed
seed and no real company, customer or transaction appears here.

## Provenance

Generated by `generate.py` in this folder with the fixed seed `20260904`; it needs `pyarrow` from
the `fixtures` extra (`uv sync --extra fixtures`). The files are committed so the eval does not
depend on the generator. 12,001 rows across `part-2025-07`, `part-2025-08` and `part-2025-09`.

## Traps

| What is in the directory | What it does if missed |
| --- | --- |
| `part-2025-09.parquet` has a `refund_reason` column the other two do not | Reading the directory returns 12,001 rows and **no `refund_reason` column at all**: no error, no warning, no nulls. A reader takes the schema from the first file in name order, and here that file predates the column. The same three files named the other way round would keep the column and null the older rows, so whether the field survives depends on the names the writer chose. |
| Order `1` appears twice in July, once at an amount everybody agrees is wrong and once at the amount that replaced it | This is what a correction looks like when the storage layer has no way to apply one. Nothing makes the second row win, and a total counts both. |
| Refunds carry a positive `amount`, as they do in the fact table | A sum that ignores `status` is high, and every month moves together so nothing stands out. |
| Three months, one file each, all small | Nothing here is big. The dataset is a demonstration that the trigger for changing storage is change, not size. |

The honest outcome reads the files individually rather than trusting one read of the directory,
reports that the column exists in one file and is dropped by a naive read, names the duplicate
order as a correction the layer cannot express, and says which of those actually justifies moving
to a table format.
